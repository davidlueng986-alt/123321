# E070-B: Direct *full-branch* R4 attack — exact-integer-gated Gram-PSD cuts inside DLX

**2026-11-07, status OPEN.** E064 canonical **branch 0 has NOT been proved UNSAT**. This report is evidence of meaningful active pruning in a full five-coordinate OA(100,5,10,2) solver, not a mathematical resolution or a count of closed first-column equivalence classes.

## Implemented, tested code

- `E070_DLX_PSD_EXPERIMENT.cpp` is derived from the existing complete E064 five-coordinate exact-cover C++ DLX. It fixes the same 19 normalized first-row and first-column points at the root, then seeks the remaining 81 five-coordinate OA points, covering all 1,000 resources.
- `E070_make_psd_features.py` prepares 19-root Schur-complement feature vectors for 100,000 five-coordinate tuples (rank-17 positive subspace and exact-root Gram pseudoinverse) using NumPy. The resulting ~13.6 MB floating feature file is regenerated by the replay script and **not** a new mathematical assumption.
- At every candidate choice, the C++ solver checks `Q_S=25I-5A_S+2J` PSD via incremental Cholesky of its Schur complement. A negative *floating* Schur pivot is **not enough** for rejection. Every actual rejection must additionally pass `verify_exact_R4_conflict`: the solver builds an approximate full vector, rounds it, then computes the exact integer identity

  `v^TQ_Sv = 50 * Σ(v_i²) + 2*(Σv_i)² - 5 * Σ_{coordinate value lines ℓ}(Σ_{i∈ℓ} v_i)²`

  with `__int128` integer sums. A choice is pruned **only if the exact result is strictly negative**. Otherwise it is retained, not marked UNSAT. This identity is equivalent to `25∑v²−5∑_{i≠j,agree1}v_iv_j+2(∑v)²`, because every pair of selected OA points shares at most one coordinate. This is a mathematically sound *necessary condition* for full OA extension.
- All original E064 exact-cover constraints, five coordinates and normalized first-column assumptions are retained. Any alleged complete branch UNSAT would still require independently repeatable global coverage/proof, which this bounded run **does not have**.

For the 18-second run: `1,989,243` R4 candidate checks, `547,452` exact integer-gated no-extension cuts, `3` candidates not exactly certified and thus kept, `235,142` ordinary exact-cover dead ends. Proof-soundness of a cut comes from its integer inequality, not the floating spectral approximation. The solver records only the first example certificate: it is rechecked **independently** with the pure-Python integer checker; the ~547k other checks are **internal to C++**, not individually saved external LRAT/VeriPB proof records.

**IMPORTANT:** The PSD solver searches **fewer** nodes in the same 5 seconds because each test costs CPU time. These logs establish pruning *power*, **not that the complete solver is faster**, and not how long a full 1/1700 proof will take. Even with exact cuts, branch0 still returned `UNKNOWN` after ~18 seconds, not full UNSAT.

## An actual solver-generated proof object

`E070_DLX_FIRST_EXACT_CERT.json` stores a full partial point set selected by the live DLX algorithm, together with a rounded integer vector which the C++ solver accepted only because its exact quadratic form is negative. Independent integer recomputation gives `v^T Q_S v = -1165` on 48 points. Thus the *first live search pruning* is independently justified, not merely inferred from a floating eigendecomposition.
